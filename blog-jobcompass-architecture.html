JobCompass Architecture: When to Use Agents vs Deterministic Pipelines

September 2026 · Vijayalaxmi Bhambure

While building JobCompass—an AI-powered career platform for UK tech job seekers— the hardest design choice was not “which model to call.” It was deciding which parts of the product should behave like adaptive agents and which parts must stay boring, testable, and deterministic.

The split

External career sites change layout, rate-limit aggressively, and present ATS forms in inconsistent ways. Those workflows need agents that can inspect the page at runtime and recover from surprises.

Internal product concerns—login, job-match scoring, application status, analytics—are predictable. They belong in FastAPI services with clear schemas, Celery jobs, Redis caching, and PostgreSQL as the source of truth. Mixing both styles in one path made the system harder to debug and harder to trust.

Scraping with guardrails

The Playwright scraper agent ingests listings from company career sites, not only aggregator feeds. Per-domain rate limiting and circuit breakers reduce the chance of being blocked; change detection flags when a site’s structure drifts so failures surface as product signals instead of silent empty scrapes.

Human-in-the-loop application automation

Fully unsupervised “auto-apply” is brittle and often inappropriate. JobCompass reads ATS forms at runtime without hard-coded site mappings, then enforces server-side confidence thresholds, daily caps, and mandatory pause gates when a field looks sensitive or the model is unsure. The agent proposes; the user (or a strict policy) confirms.

Materialised match scoring

Match quality uses semantic similarity, keyword overlap, and seniority weighting. Scores are materialised and updated with delta recomputation when profiles or listings change. That keeps list endpoints fast and avoids recomputing the entire table on every request.

Reliability and privacy as product features

Interview prep uses an LLM with a template-based fallback so a model outage does not blank the feature. For identity, I deliberately avoided approaches that pull GDPR special-category data and instead used OAuth binding plus phone verification. Privacy constraints shaped the architecture as much as latency did.

What I’d tell another builder

  • Put agents only where the environment is adversarial or unstable.
  • Keep money-path and trust-path logic (auth, caps, audit trails) outside the agent loop.
  • Prefer materialised derived data when query patterns are read-heavy.
  • Ship LLM features with a non-LLM fallback from day one.
